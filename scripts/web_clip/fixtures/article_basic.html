An open-source spec for orchestration: Symphony

By Alex Kotliarskyi, Victor Zhu, and Zach Brock

Coordinating a fleet of coding agents turns out to look less like traditional scheduling and more like conducting an orchestra where every musician can improvise­around the score while still landing on the same final chord together at the very end of the performance each evening.

The specification describes a small set of primitives that agents share when they work on the same repository at the same time without stepping on each other or duplicating effort across branches that nobody will ever merge back into the main line of development history.

At the center of the design sits a work queue that hands out bounded tasks with clear acceptance criteria so that each agent knows exactly when its own piece of the larger puzzle is finished and ready for review by a human being who understands the broader goals of the project.

symphony run --fleet small --task "migrate the parser"
symphony status --watch
symphony land --task parser-migration

State is exchanged through plain files on disk rather than through a hidden database, which means that a developer can inspect everything with ordinary tools and can reconstruct the reasoning behind every automated decision weeks after the fleet has finished its assigned work and gone quiet.

Failure handling is explicit at every level of the stack, so when an agent gets stuck it records what it tried and yields its task back to the queue instead of spinning forever on a problem that needs a fresh pair of eyes or a different strategy chosen by the orchestrator.

Observability comes from a structured event log that streams from each worker to a single dashboard where the whole run can be replayed step by step until the exact moment that something surprising happened during the night.

Security boundaries follow the repository boundary, which keeps secrets out of prompts by construction and lets teams adopt the tool without a lengthy review of a brand new trust model that nobody in the organization has ever seen or audited before this quarter began.

The reference implementation is small on purpose, because the authors want the specification itself to carry the weight while competing orchestrators experiment freely with scheduling policies that suit their own users best.

What does the reference implementation include?

A queue, a worker pool, an event log, and a command line interface that ties the three together into a single binary that runs anywhere a modern system with sufficient memory and disk space can be found today.

Adoption starts with a single command that converts an existing checklist into a queue, and teams usually see their first fully autonomous run finish within an hour of installing the tool for the very first time ever.
